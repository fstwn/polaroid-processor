# Polaroid processor: v1 scope

Decided in a scope review on 2026-10-17. Background and measurements: `.dev/REVIEW.md`. Prototype detector: `.dev/proto/proto_detect.py`.

## Goal

A robust tool that crops and rectifies high-resolution flatbed scans of instant prints. It must work unattended for agents (Claude and others) and from the command line, and produce lossless masters plus share-ready copies.

## Input

- Exactly one print per scan.
- v1: print lies in the black scanning holder (near-black, flat background). This is the precision path.
- Light background (print photographed or scanned on white paper): auto-detected from the image border since 2026-10-19 (`light.py`), white frames only.
- Input files are never written, moved or renamed.

## Formats

- Polaroid 600 / i-Type / SX-70: 88 x 107 mm quoted; 88 x 106.85 mm measured without the edge band (see "Edge band" below).
- Polaroid Go: 53.9 x 66.6 mm quoted; 53.5 x 65.8 mm measured without the edge band.
- Frame types: white, black (incl. glitter), gold/metallic, printed/coloured special editions. No per-frame-type configuration.

## Scale (px per mm)

Order of precedence:

1. Scanner profile set by the user once (named, e.g. "Epson 3200 ppi").
2. TIFF resolution tag, if it is plausible for the detected print size.
3. Assume the default format and infer px/mm from the batch median, with a warning.

The current scans are tagged 600 dpi but measure ~128 px/mm (~3250 ppi), so the tag alone is not trusted.

## Geometry

- Detection: frame-colour-agnostic (bright-speck density, per-side robust line fit, adaptive holder-noise threshold), see prototype.
- Rectification: one homography from the four fitted corners. Single resampling step.
- Edge curvature is measured per edge and reported. Above a threshold the result carries a warning suggesting flattening.
- Edge flattening: opt-in flag.
- Removed: global radial (k1) distortion correction, percentage safety crop. Replaced by a margin in mm (small default, e.g. 0.2 mm).

## Output

- Default: full print, frame included, at measured size and native resolution. No forced aspect ratio. DPI tag written from the true px/mm.
- Opt-in: photo area as an additional output, next to the full print (decided 2026-11-02, see "Photo-area crop: decisions").
- Files:
  - Full-resolution TIFF master, lossless, same bit depth as input, ICC profile carried over. Always written.
  - Derivatives as a list of named size presets (e.g. `high`, `web`), each sized by long edge or scale, each JPG or PNG.
- Tone: pixel-faithful, no colour or brightness changes by default. Heuristic shadow correction removed. Opt-in flat-field correction from a one-time calibration scan (white sheet in the same holder).

## State and failure handling

- One JSON manifest per output folder. One entry per scan, keyed by file name and content hash. Holds detection, metrics, settings used, manual fixes, status.
- Fixes keep provenance: author (human or agent), timestamp, previous value. Revertible.
- Re-runs reuse manual fixes and skip unchanged scans.
- Low-confidence detections (size off the format prior, high edge residuals, curvature warning): exported anyway, marked `needs_review` in manifest and JSON output, listed in the batch summary. `--strict` skips export instead.

## Interfaces (v1)

- Python library: typed functions (`detect`, `rectify`, `process`, ...) and result dataclasses. All logic lives here.
- CLI:
  - `--json` prints one result object per file on stdout; logs go to stderr; non-zero exit code when any file failed.
  - `--dry-run` detects only.
  - `inspect` writes zoomed corner and edge crops with a pixel grid (for humans and agents).
  - `fix` sets or nudges corners and stores them in the manifest; re-export follows.
  - Overlay preview of the detection on request.
- MCP server: thin wrapper over the library. Tools for detect, process, inspect (crops returned inline), fix, batch status.
- Claude Code skill: how to run a batch, read the JSON, review flagged prints via `inspect`, apply `fix`.
- Agent autonomy: agents may apply corner fixes and re-export without asking. Every fix is logged in the manifest. Inputs stay read-only.

## Not in v1

- GUI (planned for v2: local web UI on localhost with batch run, review grid and corner dragging).
- Multiple prints per scan, phone photos, Instax formats.
- Automatic colour grading.

## Quality targets

- Ground truth: hand-labelled corners on ~20 scans covering every frame type, made with `inspect` + `fix`.
- Every labelled corner within 0.2 mm (~25 px at current scan resolution).
- No holder pixels visible at the default margin.
- Zero crashes on all 88 sample scans.
- Regression test against the labelled set runs on every change.

## Performance

- Typical batch: 10-200 scans.
- Target: at most 6 s per scan per worker.
- Parallel workers chosen from free RAM (about 2 GB per worker), overridable.
- Resumable via manifest hashes.

## Distribution

- Installable Python package (pyproject, src layout), usable in conda or pipx.
- Console commands for CLI and MCP server.
- Windows start script for non-terminal users.

## Code base

- Commit the current state as a baseline first.
- Build the new package next to the old code; port only the useful warp and I/O ideas.
- Retire `main.py`, `shadow_corrector`, radial distortion, `border_processor` and `edge_detector` once the new CLI passes the tests (end of M1). Done: removed together with `config/processing_params.yaml` and `requirements.txt`; recoverable from the baseline commit.

### Parallel tuning (2026-10-18): no gain from worker or thread caps

Tried: workers capped at cores / 2, `cv2.setNumThreads` and TIFF threads set to cores / workers, TIFF write overlapped with the JPG derivatives. Not kept (patch in the session notes). Machine: i7-9750H, 6 cores / 12 threads, NVMe, 41 GB free RAM. The numbers below are s per scan (wall time of the whole batch / scans); the old default is 11 workers with all OpenCV threads and 8 TIFF threads each.

| Run | Old default | 6 workers x 2 threads, overlap |
|---|---|---|
| 85 scans, cold files | 4.11 | 4.24 |
| 39 scans, warm files | 4.42 | 4.34 |
| 22 scans, warm files, 3 repeats | 3.47 / 3.59 / 3.91 | 3.79 / 3.82 / 4.43 |
| 39 scans, TIFF uncompressed | 2.40 | 3.14 |

Other layouts on 39 scans (steady rate in the middle half): 8x2 3.93, 12x1 4.73, 4x3 4.68, 6x1 4.54, 6x2 without overlap 4.13, old default 4.27. Repeat runs of one config differ by up to 0.7 s per scan, so differences under about 10 % are noise. Another session shared the machine during all runs and its load was not checked per run, so every number may include contention. Two runs that overlapped another benchmark were discarded.

Findings:

- The old default already ran at 4.1 s per scan on 85 cold scans. The 4.8 s measured earlier does not reproduce.
- CPU work per scan is about 18 s single-threaded: TIFF zlib 8.3 s, warp 4.1, detect 2.3, read 1.0, derivatives 1.7. At 6 cores that bounds a batch near 3 s per scan; the batch runs at 65-80 % of it. Fewer workers do not help and uncompressed output got slower with 6 workers (more concurrent I/O hides write time).
- The only large lever is TIFF deflate (46 % of CPU): zlib level 1 runs at about 50 MB/s.
- `imagecodecs` (a regular dependency since 2026-10-19; first tried as an optional extra) makes `tifffile` encode much faster with no code change: a 108 MB crop writes in 0.67 s instead of 2.06 s on one thread, 0.15 s instead of 0.34 s on 12. Decoded pixels are identical on 3 real scans (`array_equal`), files are 6-7 % smaller. On 39-scan batches with default workers it saved 5-18 % per scan (5.33 vs 5.06, 6.43 vs 5.25, 5.70 vs 5.15 s per scan, alternating runs; the machine was slower than in the table above and may have had contention from another session). Forcing libdeflate or zlib-ng through a patch was slower than the stock `imagecodecs` path.
- Keep `opencv-python` below 5 when pinning: OpenCV 5.0.0 changes warped pixels by up to 3 levels in 0.7 % of pixels compared with 4.12.

Open findings for M3 (edge flattening):

- Many prints have slightly concave sides: the corners lie 20-60 px (0.15-0.45 mm) outside the fitted line while the middle sits on it, probably print cupping. The crop then trims a sliver of print at the corners but never shows holder.
- Some corners flare outward by up to 0.6 mm (`flare_start_px` / `flare_end_px` per edge in the manifest). The measurement is still noisy near the holder rim and on printed frames, so it is diagnostic only and sets no warning.

## Edge bias fix (2026-10-18)

The 19 labels are now human-confirmed (outline on the middle of the soft print-holder transition). Against them the detector sat systematically outward. Two causes, both fixed in `detection.py`:

- Edge points came from the analysis cells: outer cell boundary, extended outward over bright cells, and the speck threshold fires early in the soft edge. Each point is now refined at full resolution: `max(R,G,B)` averaged over the segment, 50 % crossing between the darkest holder level up to 6 cells outside and the median print level 3-8 cells inside, sub-pixel interpolated. Sparse glitter frames (contrast < 20 levels) use the speck-density profile instead, and keep the cell point when that is flat too.
- Concave sides: the robust line through all points runs outward of the side's middle, where the labeller placed the outline. Each outline is now moved to the median of the middle third of its inlier points. Edge statistics (residuals, bow, flare, inner candidates) stay relative to the robust line, so review rules are unchanged.

Detected minus label, outward positive, mm, 18 labels (known failure excluded). Script: `.dev/bias/measure.py`.

| side | before: median (range) | after: median (range) |
| --- | --- | --- |
| top | +0.026 (-0.000..+0.100) | -0.005 (-0.040..+0.050) |
| right | +0.072 (+0.009..+0.115) | +0.012 (-0.021..+0.029) |
| bottom | +0.038 (+0.000..+0.086) | -0.019 (-0.043..+0.012) |
| left | +0.080 (-0.022..+0.122) | +0.013 (-0.030..+0.030) |
| worst corner | 0.152 | 0.095 |

Regression tolerance tightened from 0.2 mm to 0.1 mm. The worst corner is the black glitter frame `tttacho_13-2` (density fallback). The remaining spread (about +-0.04 mm per side) is close to the label noise: on long, soft ramps (bottom edges, cupped top edges) the labeller's choice varies between scans. The parameters were chosen on the same 18 labels, so new labels should be checked before tuning further.

88-scan dry run (one output folder per input folder, `.dev/bias/run/`): 88/88 detected, 0 crashes, 87 `ok`, 1 `needs_review` (`250928_SICKalps_L2_D3_29 (2)`, same rim case and hint as before). No new review cases, but two of the three M1 review cases now pass by a hair, although both edges are still not straight:

- `260315_Polaroids_Samsoe_02`: the right edge is S-shaped. The refit line is more vertical now, so `not_parallel:left-right` dropped from 0.32 deg to 0.27 deg (rule: 0.3). The bottom-right corner sits about 40 px outside the print, the old outline was worse there.
- `260328_RollerRoids_tttacho_14-2`: black glitter frame with a concave left edge. Left inliers went from 13/23 to 14/23 (rule: share 0.6). The five middle points that sit 21-36 px inside the line are outliers, so the outline in the middle of the side runs about 0.25 mm outside the print, more than the 0.2 mm margin.

Both show that the review rules missed a curved edge whose middle points are rejected as outliers. New rule `edge_inside:<side>:<mm>`: per side, the deepest run of three consecutive edge points (outliers included) inside the outline; above the crop margin, holder would show in the export, so the scan needs review. On the 88 scans every good scan stays at or below 0.07 mm. Flagged: `tttacho_14-2` (right 1.23 mm, left 0.24 mm), `tttacho_16-2` (left 1.75 mm, right 0.60 mm; black glitter, previously `ok`), and `D3_29 (2)` (bottom 0.55 mm, alongside its rim hint). Result: 85 `ok`, 3 `needs_review`. `Samsoe_02` stays `ok`: its S-shaped right edge bulges outward at the bottom, so the crop trims print there but shows no holder.

Detection time is unchanged: 3.3 s per labelled scan with 4 parallel jobs (3.5 s before). The refinement averages about 100 small full-res windows per attempt.

## M3 part 1: curled prints and edge shadows (2026-10-19)

Both run by default in `process` (`--flatten off`, `--shadows off` to disable).

- **Flattening** (`flatten.py`): each side is traced every 0.5 mm at full resolution (50 % crossing between holder and print, plateau check against the holder rim), fitted with a robust 4th-degree polynomial, and checked per side: at least 80 % of samples agree, no gap over 12 % of the side, scatter below 0.05 mm, bend below 1.6 mm. Reliable sides that bend 0.1 mm or more trigger an unwarp (coarse map every 16 px, 0.002 px error). Unreliable sides stay straight.
- Measured on curled prints (95th-percentile deviation of an edge from straight, export extended 1.5 mm): D2_29 left 0.73 -> 0.04 mm, D2_28 right 0.47 -> 0.03 mm, D3_17 (gold) left 0.37 -> 0.04 mm, Scan_04 right 0.19 -> 0.02 mm. All sides within 0.042 mm after unwarping. Printed and black-glitter frames: most sides are not reliable and stay straight; tttacho_13-2 and Samsoe_04 are not flattened.
- **Edge shadows** (`shading.py`): on white frames the border darkens 3-18 % at 0.25 mm from the edge (bottom strongest) and the effect reaches about 1.5 mm in. Measured per 1 mm window from the border, corrected only where the frame is plain, has no steep drop (graphic edge) and is flat from 1.5 mm inward, and only on sides measurable over at least half their length. White frames come out even (1.00 relative to 3 mm in, every side); gold, olive, printed and black frames are currently left untouched (their own gradients do not look like a shadow).
- Cost: tracing about 1-2.5 s, unwarping about 3.6 s instead of about 1 s for the homography, shading about 1 s per scan.
- Visual check (2026-10-19, `.dev/compare`, 20 library scans, straight vs flattened vs flattened + shadows): flattening and shadow removal approved on all 20. One finding: on round-window prints the first version (a Coons patch, side corrections blended linearly across the whole print) made the circle slightly oval.
- Measured against the photo window, whose border is a straight line (square windows) or a circle (round windows): in a plain rectification the window border stays straight within about 0.05 mm even where the outer edge bends 0.3-0.6 mm, so the distortion is confined to the border of the print. Coons bent the window border by up to 0.08 mm (Misc_21 left, D3_08 bottom, Garten_0 right) and raised the circle's axis ratio (D2_02 1.0042 -> 1.0080).
- Fix: each side's correction fades out with a raised cosine within `fade_mm` = 5 mm of the edge (the side frame is about 6 mm wide); further in, the map is the bilinear map between the corners. Square window borders now match the straight export within 0.008 mm; circle axis ratios D2_27 1.0065 -> 1.0036, D2_29 1.0076 -> 1.0044, D2_02 1.0042 -> 1.0063 (Coons 1.0080). The edges are still exactly on the traced curves.
- Not done: shadow correction for gold and coloured frames; the slight darkening across a whole lifted area (about 3 %); flattening for manually fixed outlines (they stay straight).
- Skewed photo window (seen in the visual check, measured 2026-10-19 on the 58 square-window library prints): the faded unwarp still used the corners where the side curves meet. Those are extrapolated into the rounded print corners and landed up to 0.85 mm off the corners of the fitted lines (mostly bottom right), so the window's left and right borders were 0.21 deg off parallel (median; 0.45 max) against 0.10 in the straight export. Fix: the base map is now the straight export's homography from the quad, and each side adds its traced offset near the edge only; within 2 mm of a corner (`end_skip_mm`, no trace samples there) the offset is held instead of extrapolated. The window now matches the straight export on every scan (rotation, shear, parallelism within 0.005 deg; round windows identical), the output size equals the straight export's, and the exported edges of the eight most curled prints are straight within 0.007 mm (95th percentile).
- What remains is in the prints: the straight export shows the window rotated 0.08 deg (median) against the frame, about 0.3 deg sheared on the whole D3 batch (D3_05 to D3_12) and rotated 0.3-0.5 deg on Misc_22 to 24. Cropping cannot fix that without distorting the frame.
- Library run (2026-10-19, all 119 scans of the five library folders, dry run plus flatten and shadow removal in memory; `.dev/library_run`): no outline moved (0.00 mm on all 118 detected scans). 109 ok, 9 needs_review, 1 failed (the emulsion lift), against 104 / 14 / 1 before flattening. The five scans that left review lost a `not_parallel` flag: four curled prints (D2_18, 27, 28, 29), and Misc_22, where the bottom line had been fit on the holder rim but the trace found the true print edge, so the flattened export no longer shows holder. The parallel-rim cases (D2_13, D3_29 (2)) and D3_10 stay flagged by `size_outlier`.
- Flattened 105 of 118; max bend per scan median 0.28 mm, 90th percentile 0.49 mm, largest 0.66 mm. Not flattened: 13 printed / glitter frames (Samsoe, tttacho_13, 14, 16, 21, Misc_03) whose sides are not reliable.
- Shadows corrected on 89 scans: 82 on all four sides, 7 on two or three (one side measurable on only 13-45 % of its length, so that side keeps its shadow); 29 untouched. Largest darkening per side median 11.5 %, max 30 %.
- Chords between the curve corners are not a usable parallelism check: curled prints show 0.3-0.4 deg between left and right chords because the curve ends are extrapolated into the rounded corners.

## Size-proven rim refit (2026-10-20)

When the holder rim runs parallel to one side, the detector can take the rim's outer edge for the print edge; only the batch shows it (the print is oversized along one axis). `refit.py`, run in the pipeline only for scans flagged `needs_review` and oversized along exactly one axis against the median print of their group:

- an inner line the detector already found (`inner_px`, the old `hint:fix --shift`) that explains the oversize within 0.15 mm: the side moves onto it (D2_13, D3_29 (2): bottom -0.54 mm; D3_29 (2) then matches its label within 0.051 mm);
- otherwise a dark seam behind a rim band (the print's edge shadow between rim and print), searched at full resolution on both sides of that axis; it must be found on at least 60 % of the side, on one side only, and the refit line must explain the oversize within 0.15 mm (D3_10: bottom -0.52 mm, seam 0.25 deg tilted against the rim line).

The scan then passes review with an informational `rim_refit:<side>:<mm>`; the detected outline stays in the manifest as `quad_detected`, and the curves are traced again. Library dry run: the three rim cases are ok, the other 115 outlines are unchanged. Still flagged: D2_26 (0.4 mm wider, edges look right), the black glitter frames (Samsoe_05/06/09, tttacho_14/16) and the emulsion lift.

Tried and dropped: re-detecting a black Go frame on the black holder (sample 73) with low speck thresholds and accepting it when it has a format's size. Thresholds 5-7 give 54.1 x 64.4 mm with the bottom edge still inside the wide black bottom frame; a size check alone could accept such an outline, so 73 stays a known failure.

## v2 web app: decisions (grilling session, 2026-11-01)

A local web app for the whole workflow, replacing `polaroid review`. Decided with the user, one question at a time:

1. **Scope:** the full loop in one place: pick input folder, run, watch progress, review grid, drag-to-fix, export. No image editing, no library management.
2. **Tech:** the standard-library HTTP server and plain JavaScript, as the review page today: no build step, no new dependencies, one `pip install`; the drag-to-fix code is reused.
3. **Input folders:** a Browse button asks the local server to open the native Windows folder dialog (tkinter); a path field as fallback; recent folders remembered.
4. **Output:** default `<input>_processed` next to the input (as the drag-and-drop launcher), shown and editable before the run; one output folder per input folder.
5. **Run model:** Detect first (persisted in the manifest, no exports), review and fix, then Export; plus a one-click Detect + export for trusted batches.
6. **While running:** the grid fills live, finished scans can be opened and fixed, a progress bar shows done/total and time left, Cancel stops the run (see the status section), a new run resumes from the manifest.
7. **Projects:** home lists recent projects (input + output folder) with counts (ok / needs review / exported); one project open at a time; any existing output folder can be opened, including CLI-made ones.
8. **Grid cards:** a straightened crop preview (what the export will look like), made once during detection and cached in the output folder; status badge and warnings; filter by status; a click opens the 9-tile drag view.
9. **Settings:** a per-project panel (stored in the manifest as today): margin, JPG derivatives (high / web), flatten and shadow correction visible; scale/profile, TIFF compression, interpolation and overlay under Advanced; the last choices become the defaults for new projects.
10. **Launch:** `polaroid app` starts the server and opens the browser; `polaroid review <folder>` opens the app on that project (the old page goes away); `launcher/polaroid-app.bat` to double-click, folders dropped on it become new projects.
11. **Alongside CLI and agents:** the app reloads a project when its manifest changes on disk (agent fixes show up live); a lock file allows one run per output folder; single fixes are small atomic writes and may happen anytime.
12. **Delivery:** three slices, each committed and shown to the user: (1) projects home, Detect run with live grid and crop previews; (2) drag-to-fix in the app, Export with progress, cancel/resume, run lock and live reload; (3) settings panel, `polaroid app` / review shortcut, the .bat launcher, docs and skill update.

### v2 web app: status (2026-11-01)

All three slices are done. The code is in `src/polaroid_processor/app/` (server, project, store, settings, fix, launch; static page) next to the review page it reuses (`review/`), and `lock.py`, `preview.py`, `manifest.py`. What was decided on the way, beyond the twelve points:

- **Previews** (`preview.py`): the crop is cut out, shrunk to a 600 px long edge and rectified or unwarped along the traced curves; shadow correction is left out. A key of outline, curves, margin and size says when a preview is stale; the app renews stale ones one at a time while no run goes.
- **Run lock** (`lock.py`): an operating-system lock on a byte of `polaroid-run.lock` (`msvcrt.locking` / `fcntl.flock`), taken in `run_batch`, so CLI, MCP and the app are covered, and a crash releases it. `RunLocked` is a `ValueError` (CLI exit 2). `fix --export` stores the fix and skips the export with a note when the lock is taken.
- **Merge before save** (`manifest.py`): `save()` re-reads the file under a file lock and merges per scan (a scan only one side changed comes from that side, else field by field; `history` keeps both). `refresh()` merges without writing. The batch re-judges scans fixed by others (`take_fixed`) before it exports and before it builds its summary, and saves at most every 1.5 s while jobs finish.
- **Export identity**: `export_key` as before; `export_base` is the key without the scale value, and includes the scale source and `ppi` / `profile` for explicit scales. A finished export whose base is unchanged and whose cut scale (`export_geom_ppm`) is within 0.5 % of the new inferred scale, with the same flatten decision, gets its resolution tags patched (`retagged`); anything else exports again. Fresh exports of the same run follow the same rule. The app's Export count is computed with the same keys, so settings, fixes and scale changes show in it.
- **Settings** are the manifest's `settings` (as the CLI writes them); a project without a manifest keeps them in `app.json` until its first run. The last panel choices are the defaults for new projects, except `ppi` and `profile`, which belong to a scanner setting. They cannot be changed while a run goes (the run reads its settings once).
- **Launch**: `polaroid app [FOLDER...]` and `polaroid review OUTPUT` start the server on 127.0.0.1:8780 (a free port when that is busy and no `--port` is given) or reuse a running app (found by `/api/ping`) and open the browser on it. The standalone review server is no longer started by any command; `review/` stays as the code behind the app's fix page.
- **Cancel** (changed after the user's first test): it stops the work in flight, not only the scans not yet started. `_run_pool` submits about the worker count plus two jobs at a time, checks `cancel()` four times a second, yields the results already in, then terminates the worker processes (and closes the call queue's reading end, else the executor waits for ever on its feeder thread). The scans cut off are not done and the next run redoes them; a cut-off export loses its `export_key`. Exports write to `NAME.part` and rename, so no partial file has a final name; a run removes the leftover `*.part` files at its start (not in `_previews/`). After a cancel the run skips size refits and the export pass. The CLI's Ctrl+C is unchanged.
- **Fix page in the app**: no `beforeunload` guard (the app closes the page; a save leaves nothing unsaved); the Grid button asks in the page before it drops unsaved drags. The standalone page keeps the browser's guard.
- **Not done / ideas**: image editing and library management stay out of scope (decision 1); a "Detect again" of every scan (`--redetect`) and the strict export (`--strict`) are CLI only; export of a chosen subset of scans; per-scan margin.

## Photo-area crop: decisions (grilling session, 2026-11-02)

The user's goal: the crop to the photo area as an *additional* output, not instead of the full print. The full-print export (frame included) stays exactly as it is and is always written. Decided with the user, one question at a time:

1. **Layout:** the photo crops go to `<out>/photo/`, mirroring the full print: `photo/high/<stem>.jpg` and `photo/web/<stem>.jpg` with the same derivative list as the full print, and optionally a master `photo/<stem>.tif`. File names equal the full print's, so pairs line up.
2. **Setting:** one three-state option `photo_crop` = `off` | `derivatives` | `tiff` (derivatives plus the TIFF master). Default `off`. Per project in the settings panel (a dropdown), stored in the manifest settings, CLI `--photo-crop {off,derivatives,tiff}`, API and MCP. It is part of the export key, so changing it exports again.
3. **Finding the window:** measured per scan by a border scan (as `.dev/compare/measure.py`: from each side inward past the frame, first drop below the frame level), with line fits (square windows) or an ellipse fit (round windows). The nominal window size per format is only a plausibility check; a mismatch means "window not found". No nominal fallback crop.
4. **Rotation and shear:** the window is rectified to its own border. Its four border lines give a window quad, which is warped straight from the original scan (one resampling, as the full print). So a window rotated or sheared against the frame (up to 0.3-0.5 deg on some batches, see M3 part 1) comes out square to its own border. On flattened prints the window lies inside the fade-out zone, where the unwarp is the straight homography, so the quad maps back to the scan directly.
5. **Round windows:** a tight square around the fitted circle. The TIFF master (when on) gets an alpha channel, transparent outside the circle. The JPG derivatives keep the frame pixels in the four corners.
6. **Bleed:** the crop cuts `photo_bleed_mm` inward past the fitted border on every side, default 0.3 mm, a setting next to the margin (panel and CLI). It hides the soft step and the thin dark line at the window border.
7. **Failure:** when the window is not found or fails the size check, the full print is exported as always, no `photo/` files are written for that scan, the manifest gets a warning, and the scan is `needs_review`. A failed window never fails the export.
8. **Stage:** the window is found at Detect, on a reduced-size straightened copy in memory, and its quad (or circle) is stored in the manifest; Export uses the stored window. Review rules, the grid and the drag view see it before any export. The window step runs only when `photo_crop` is not `off`. Turning the option on for a detected project runs the window step for scans without a stored window, not a full re-detect; a hand fix of the print outline runs it again for that scan.
9. **Review:** the drag view draws the window outline in a second colour with four draggable handles (round windows: the circle, edited through its bounding square). The MCP `polaroid_fix` can set window corners too. Accepting a scan without a window means: export without photo crop.
10. **Camera shots:** the photo crop applies to them as well, with the same window finder on the straightened copy.
11. **Invariance:** print outlines never change because of this feature, and Detect with `photo_crop` off produces the same results as before.

### Photo-area crop: slice 1 status (2026-11-02)

6. **Interfaces:** `fix` / API / MCP `polaroid_fix` get window corners (set, nudge), kind, no photo crop and reset; `inspect` (CLI, API, MCP) can centre its tiles on the window.

What was built:

- **Stored shape (revised after review, 2026-11-03).** The user's window choices are in their own field, `entry["window_fix"]`, which only `fix_scan` writes (like `override`; the field-level merge of two writers keeps it, so a run cannot overwrite it). `entry["window"]` is the automatic window only (batch-owned). `window_fix = {"window": <hand-set window | no-photo-crop choice | null>, "accepted": <accept mark | null>}`, and is `null` when both are empty. A hand-set window is a window dict (`found: true`, `kind`, `quad`, `size_mm`, `format`, `source: "manual"`, `author`, `at`, `note`). "No photo crop" is `{"found": false, "reason": "no photo crop by choice", "source": "manual", author, at, note}`. The accept mark is `{"outline": <outline id>, "author", "at", "note"}`. History entries `window`, `window-none`, `window-reset` (by a fix) and `window-drop` (by a run, when the scan file changed) carry `window_before` and `window_after` (the previous and the new choice; `Manifest.set_window_fix`). `fix --reset-window` sets the choice to `null`.
- **Window in force** (`scan_window.effective_window`): the hand-set window when all four corners lie inside the effective outline (`fix_in_force`), else the no-photo-crop choice (holds for any outline), else the automatic window. The export, the export key, the status and the page use it; the run measures the automatic window (stale: `auto_valid` compares its `outline` with the outline's id) whatever the user chose, and never stores the choice. A hand-set window survives a re-detect and a refit; it is dropped (with the whole `window_fix`) only when the scan's content changed (fingerprint), the one place where the batch writes the field, like the outline override.
- **Hand-set window outside the outline.** `evaluate` flags it (`fix_outside`): warning `photo window set by hand lies outside the print outline`, `needs_review` unless accepted; the automatic window is used in the meantime. There is no drop logic in `fix_scan` any more. `reset_window`, a new window inside the outline, or an outline that contains it again clears the flag.
- **Review rule.** A not-found window in force raises `photo window not found: <reason>` and `needs_review`, current or not, unless the accept mark matches the outline (`accept_valid`). `fix --accept` stores the mark for the outline the scan has after that fix (`--set ... --accept` in one call too), but only while there is something to accept: the window in force is missing or a hand-set window lies outside the outline (so an accept given while a window was found cannot cover a later miss). It lapses when the outline changes, is revoked by `fix --reset` of the outline (an accept stores the detected outline as override, so its id would otherwise still match), is dropped with the whole `window_fix` when the scan file changes, and survives windows being measured again. With a hand window outside the outline the automatic window is cut (no photo crop when that is missing too), also after an accept; the page says so. `inspect --of window` and the window record show the hand corners then (what `window_nudge` edits). Old manifests (decided in review: no handling): a slice 2 accept that lapses at a re-measure re-flags the scan, one Confirm restores it (`test_a_slice_2_accept_lapses_when_the_window_is_measured_again`). Old manifests, rule: an automatic window without `accept_needed` (made before slice 3) keeps the old rule, any override accepted it, so such scans stay `ok`; as soon as the window is measured again it gets the new rule.
- **Export identity.** An export job returns `export_window` (the window it cut the photo from). The key is computed from it, and a scan exported in pass A is retagged and stamped only when outline and window shape match the ones it has at the reconcile step; otherwise it goes into the export pass of the same run (before, a window fix saved during a run was stamped on photo files cut from another window).
- **Nominal placement** (`scan_window.nominal_window`): `window.NOMINAL` (left, top, width, height in mm from the print's top left), scaled by print width over format width and mapped through the inverse of the print homography. Choice of kind: both are offered in the drag view (Place square window / Place round window; round for the 600 only); `fix` / API take `window_kind`, default the kind most scans of the batch have (round only on a majority, else square). The nominal window of the synthetic test prints lies within 1 mm of the true one.
- **Drag view** (`review/static/index.html`): "Photo window" section (state line, Print outline / Photo window mode, Place square / round, Square / Round, No photo crop, Back to automatic). Window mode cuts the tiles at the window's corners and edge midpoints (`/tiles?of=window[&kind=...]`), the handles are cyan, Save correction stores print and window changes in one fix (`POST .../save` with `corners` and `window`; both or neither, so a refused window leaves the outline unsaved too and a retry adds no second entry). Confirm accepts a missing window. Routes: `POST .../window` with `{corners, kind}`, `{none: true}` or `{reset: true}`. Window corners must run clockwise (positive signed area in image coordinates), checked in `api.check_window_quad` and in the page. A refresh of the page while a run measured another window (no history entry, so `rev` is unchanged) takes the new window over unless the window has unsaved edits.
- **Round windows** are drawn and cut as the ellipse inscribed in the four corners (`photo_image` alpha, `render.circle_of`, the page); for a square crop it is the circle of before. Decided after review: the draw/cut mismatch of a hand-set non-square round window is fixed by cutting the ellipse, dragging stays free.
- **Grid cards** show the window in force as a cyan outline over the crop preview (position through the print homography; a flattened print is drawn as if straight) and tag a hand-set window "window by hand" and the no-photo-crop choice "no photo crop" (record field `window_fix`: `hand` | `none`, only while the choice is in force).
- **Interfaces.** CLI `fix --window-set/--window-nudge/--window-kind/--no-photo-crop/--reset-window`, `inspect --of window`; API `fix_scan(window_sets, window_nudges, window_kind, no_photo_crop, reset_window)`, `inspect_scan(of="window")`; MCP `polaroid_fix` / `polaroid_inspect` the same, with texts that say when to use them; window records have `state` (found, missing, none) and `source`. ## Export metadata: decisions (2026-11-22)

The user's goal: per-project metadata (title, author and so on) written into every exported file. Today the TIFF masters carry tifffile's default description `{"shape": [h, w, 3]}`, which viewers show as the title, and the JPGs carry no text metadata at all. Decided with the user:

1. **Fields** (all optional, per project): title, author, copyright, description, keywords (a list), date taken.
2. **Placeholders** in the text fields, filled per scan: `{stem}` (the scan's file name without extension, as the export name), `{n}` (the trailing number of the stem, e.g. `17` for `..._D3_17`; empty when the stem ends in no number), `{project}` (the input folder's name), `{format}` (`600` or `Go`, from the scan's format). `{{` and `}}` give literal braces. An unknown placeholder is an error when the setting is saved (CLI exit 2, API `ValueError`, the app's panel shows it), never at export time.
3. **Date taken:** one value per project, `YYYY`, `YYYY-MM` or `YYYY-MM-DD` (Polaroids are often known to the month only). XMP gets it at the precision given; the EXIF field, which needs a full date and time, only gets a full date (time 00:00:00). Checked when saved.
4. **Scanner tags:** `Make` and `Model` of the scan are carried over. `Software` becomes `polaroid-processor <version>` (today the scan's SilverFast string or tifffile's name). Nothing else from the scan's EXIF (the scanner's maker note) is carried.
5. **Where it goes:** every exported file: the full-print TIFF master and its derivatives, and the photo crops (`photo/`). Not the cached previews (`_previews/`) or overlays. One XMP packet is the authoritative copy in every format (TIFF tag 700, JPEG APP1 `http://ns.adobe.com/xap/1.0/`, PNG `iTXt` `XML:com.adobe.xmp`): `dc:title`, `dc:creator`, `dc:rights`, `dc:description`, `dc:subject`, `photoshop:DateCreated` / `exif:DateTimeOriginal`. Next to it, the legacy fields that common viewers read: TIFF and EXIF `ImageDescription`, `Artist`, `Copyright`, `DateTimeOriginal` (full dates only), and the Windows `XPTitle` / `XPAuthor` / `XPKeywords` / `XPComment` tags, so Windows Explorer shows them. Text is UTF-8 (umlauts must survive) in XMP and the XP tags; the ASCII TIFF/EXIF fields get UTF-8 bytes too. An empty field writes nothing; with no metadata set, a file carries only Make, Model, Software, resolution and ICC, and no `ImageDescription`.
6. **Changes after export:** metadata is not part of the export key. Each export records a separate metadata key (the filled values); when the project's metadata changes, a run rewrites the headers of the existing files in place, pixels untouched (as `retagged` does for the scale), and counts them as `metadata_updated`. A file that cannot be patched in place (unexpected structure) is exported again rather than left wrong. The app's Export count includes these scans.
7. **Settings and defaults:** stored in the manifest's `settings` as `metadata` (left out when empty, so manifests without metadata are unchanged). CLI `process --title/--author/--copyright/--description/--keyword (repeatable)/--date-taken`, `api.make_settings(metadata=...)`, MCP `polaroid_process` (a `metadata` object), the app's settings panel (a "Metadata" group). As with the photo crop, a run that leaves metadata out keeps the project's values; a field set to an empty string clears it. In the app, author and copyright of the last panel choice become the defaults for new projects; title, description, keywords and date taken do not (they belong to a project).
8. **Invariance:** the pixels, outlines, windows and export keys are unchanged; only file headers change. Existing exports without a metadata key get their headers rewritten on the next run once metadata is set (the `{"shape": ...}` description is removed then too); with no metadata set they are left alone.

Follow-up to export metadata slice 2: the three review nits and the user's request to list existing scanner profiles in the settings panel. CLI and MCP are unchanged.

- **Nit A (page test).** `tests/test_app_page.py` runs the real `app.js` in Node against a small DOM stub (`tests/js/page_harness.js`, from the reviewer's harness; a textarea turns `\r\n` into `\n`, a select keeps a value only when an option has it). The test of the save logic replaces the source-text test: a margin-only save sends no metadata (comma keywords and a CRLF description stay), a title edit sends the title only. - **Nit B (empty merge).** `metadata.merge` skips the 8000-character check when the given fields set nothing: `{}`, only `None`, or only clearing (`""` / `[]`). Clearing never makes the total longer, so it is not refused either. MCP `metadata: {}` or `{"title": null}` on a project already over the limit runs and leaves the saved values as they are. A call that sets a field is checked as before.
- **Nit C (message).** When the merged total is too long, the message names the saved fields that count: `metadata texts add up to more than 8000 characters, with the output folder's title, description: shorten or clear one`. A field the call itself replaces is not listed as saved; when the call alone is too long (nothing saved counts) the message is the plain one. Same text on the CLI (exit 2), `api.process` (`ValueError`) and the panel (400, under `fields.metadata`).
- **Dropdown.** The "or scanner profile" text field is a `<select>`: "none" (the scale comes from the ppi field, the scan's tag or the print size), then every profile of the profiles file the project uses as `name (3200 ppi)`, sorted by name (ignoring case). The file is `profiles_path(settings.profiles_file)`: the project's own, else `$POLAROID_PROFILES`, else `~/.config/polaroid-processor/profiles.yaml`. The server reads it: `GET /api/project/settings` (and the answer of a save) has `profiles: {path, items: [{name, ppi}], error}` (`app/settings.profile_options`; a file that cannot be read gives an empty list and `error`, the panel still loads). The page builds the options (`fillProfiles`) and sends `profile` only when the choice changed. No profile editing in the app.
- **A saved profile that is not in the file** stays as an extra, selected option `name (not in profiles file)`, with an amber hint. Rule (decided by the user, "allow other saves"): `from_panel` checks a profile against the profiles file only when a save sets or changes it, so a settings save that does not change `ppi` or `profile` passes with a saved profile the file lacks, and a save that sets or changes the profile to an unknown name is refused (400, `scanner profile 'x' not found in <path>`). Before, the check ran on every save, so such a project could not save anything (the old text field behaved the same). A run with the missing profile fails as before with `scanner profile 'x' not found in <path>` (the app's run state shows it). Naming the saved profile again is no change. The `ppi`-or-profile rule still applies after the update, so a ppi typed while the missing profile is saved is refused as "both". The hint says runs fail until the profile is replaced or added, and offers the safe way out first: in one save choose "none" and type the profile's ppi (checked: switching from a profile to the same ppi exports nothing, because the export key holds the scale value, not its source); "none" alone infers the scale, which may differ by more than the tags-only tolerance and export the project again. Pinned by `test_an_unrelated_save_passes_with_a_saved_profile_missing_from_the_file`, `test_a_run_with_a_saved_profile_missing_from_the_file_still_fails_with_its_message`, `test_choosing_another_unknown_profile_is_refused_a_known_one_accepted`, `test_none_with_the_ppi_in_one_save_replaces_a_missing_profile` and `test_a_ppi_without_clearing_a_missing_profile_is_refused_as_both`.
- **Either ppi or a profile** keeps its rule and message (`set either ppi or a scanner profile, not both`); the page shows the server's message. With no profiles file or an empty one the select has only "none" and a hint with the file's path and the shape `profiles: {name: ppi}`. A line under the scale fields says that changing the scale of an exported project exports it again (the footer already says it).
- **Grid with a missing profile (review fix).** A project with a manifest whose saved profile the file lacks used to answer 500 on `scans` and `progress` (`Project.snapshot` calls `reevaluate` and `export_plan`, which resolve the scale and raise `KeyError`), so the page had no grid. `snapshot` now looks the scale up first (`project.scale_problem`: `explicit_scale` for the saved ppi or profile, inside `try/except Exception`) and only when that passes runs `reevaluate` and `export_plan`, unguarded as before, so a bug there stays a loud error and is not shown as a scale error. A missing profile gives the run's message; a profiles file that cannot be read (broken YAML, a list instead of a mapping, a value that is no number) gives `the profiles file <path> cannot be read (<Error>: <first line>)` and is logged. The snapshot also notices a change of the profiles file the saved profile is looked up in (its stamp is kept with the cache), so fixing the file clears the message without a restart; the stamp is part of `rev` too, so the page re-reads the scans (and their export tags) when the file changes. The unreadable-file warning is logged without a traceback. With that, the scans are listed as before (status, preview, warnings), without export states (`export` is null), `counts.to_export`, `to_retag` and `to_headers` are 0, and both answers carry the message as `scale_error` (else null).
